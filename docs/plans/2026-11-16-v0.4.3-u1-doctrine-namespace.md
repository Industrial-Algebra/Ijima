# v0.4.3 U1 — Doctrine namespace configuration (the fossil fix)

## Unit

The wake-up doctrine section reads the hardcoded
`DOCTRINE_NAMESPACE` (`ns_doctrine`), which production never ingests
into — its 830 doctrine rows live on `ns_ia_doctrine`. The section
has been silently empty since before 0.4.x (found by the retrieval
ledger on its first day; dispositioned twice). This unit makes the
wall configurable: a config key, public default unchanged, deployment
overrides at the daemon layer.

**Depends on:** nothing.
**Followed by:** U2 (the registry generalizes wall addressability).

## Contracts

### `config.rs` — field

```rust
    /// The wall wake-up's doctrine section reads (v0.4.3 fossil fix).
    /// Default `ns_doctrine` — the public default is unchanged; a
    /// deployment whose doctrine lives on an org wall sets this
    /// (e.g. `ns_ia_doctrine`).
    doctrine_namespace: Option<String>,
```

(Inside `IjimaToml`, matching the file's field style; `Option` with
`None` meaning "use the default".)

### `api.rs` — WallConfig + layer + handlers

```rust
/// Deployment-configured wall routing (v0.4.3 U1). Defaults keep the
/// pre-0.4.3 behavior: doctrine reads `DOCTRINE_NAMESPACE`.
#[derive(Clone)]
pub struct WallConfig {
    /// The wall wake-up's doctrine section and the doctrine routes
    /// treat as the doctrine wall.
    pub doctrine_namespace: NamespaceId,
}

impl Default for WallConfig {
    fn default() -> Self {
        Self {
            doctrine_namespace: NamespaceId::new(
                ijima_core::namespace::DOCTRINE_NAMESPACE,
            ),
        }
    }
}
```

Router wiring: `app(...)` keeps its exact current signature and
delegates to a new `pub fn app_with_walls(...)` whose parameter list
is app's plus `walls: WallConfig`, layering
`.layer(Extension(Arc::new(walls)))` — `app()` calls it with
`WallConfig::default()`. Every existing test call site of `app(...)`
is untouched.

Handlers: every site that currently constructs
`NamespaceId::new(ijima_core::namespace::DOCTRINE_NAMESPACE)` (the
wake-up handler's `doctrine_ns`, `resolve_doctrine_read_ns`'s
`default_ns`, and any doctrine route resolving the default wall)
reads `walls.doctrine_namespace` from a new
`Extension(walls): Extension<Arc<WallConfig>>` parameter instead.
The const stays as the default's value — grep for
`DOCTRINE_NAMESPACE` in api.rs and convert every handler-side use;
the core const itself is untouched.

**Semantics (contract reviews rounds 1+2 — read this before
converting anything): doctrine-ness moves WITH the configuration,
but ordinary wall access does not.** The conversion is ENUMERATED,
not blanket — convert exactly these sites (the doctrine-route
identity: the configured wall is *the* doctrine wall for destination
AND doctrine authorization):
- the wake-up handler's `doctrine_ns` (read source),
- `resolve_doctrine_read_ns`'s `default_ns` — both the None-branch
  destination and the `requested == default_ns` branch test,
- `ingest_doctrine`'s default destination and its explicit-target
  prohibition comparison,
- `rollback_doctrine`'s default destination (api.rs ~990 — round 3
  P2: an unqualified `POST /doctrine/rollback` must target the
  CONFIGURED wall, consistent with configured ingest and version
  reads; its explicit `?namespace=` target keeps going through
  `resolve_ns` unchanged).

PRESERVE the old constant at exactly these sites (round 2, P2:
ordinary-access policy — the old wall stays an OPEN wall, which is
doctrine's public-read design, not an accident):
- `resolve_ns`'s open-whitelist entry (api.rs ~251–253):
  `ns_doctrine` remains open-readable on ordinary routes,
- the promotion handler's open-target entry (api.rs ~781–783):
  `ns_doctrine` remains an open promotion target.

The CONFIGURED wall's ordinary-route access keeps its own rules
(membership/admin as an org wall); its doctrine-ness expresses only
through the doctrine routes and the wake-up section. Consequence 1
of round 1 is therefore precise: an explicit `?namespace=ns_doctrine`
request under configuration reaches the ordinary open-wall path —
which is a 200 with an empty list for an unwritten wall, and stays
readable for a non-member, because the open whitelist keeps the old
constant.

Consequence 2 (round 2, P2): the prohibition an explicit
configured-wall ingest hits lives in `POST /doctrine` —
`ingest_doctrine` — NOT in the memory route (`/memories` goes
through `store_memory`'s ordinary checks and never consults the
doctrine prohibition). The regression below exercises the doctrine
route itself.

### `main.rs` / `server.rs` — plumbing

At the single production `app(` call site, build `WallConfig` from
the loaded `IjimaToml` (`doctrine_namespace` field mapping to
`NamespaceId::new(v)` when present, default otherwise) and call
`app_with_walls`.

## Tests (api.rs `mod tests`)

1. `wakeup_reads_configured_doctrine_wall`
   - Build via `app_with_walls` with `doctrine_namespace =
     NamespaceId::new("ns_cfg_doctrine")`; seed one memory there and
     one on the default `ns_doctrine`.
   - GET `/wakeup`: doctrine section serves exactly the configured
     wall's memory; the default wall's memory is absent.
2. `default_app_unchanged_doctrine_wall`
   - Plain `app(...)`: seed `ns_doctrine`, GET `/wakeup`, doctrine
     section serves it (the default path byte-identical in behavior).
3. `doctrine_routes_respect_configured_wall`
   - With `app_with_walls`: POST `/doctrine` ingests to the
     configured wall (verify via recall on that wall; the default
     wall stays empty).
4. `old_default_wall_becomes_ordinary_open_under_configuration`
   - `app_with_walls` with doctrine = `ns_cfg_doctrine`; a
     memory:read token (NO doctrine caps, NO admin, NOT a member of
     `ns_doctrine` — note the open whitelist keeps the old wall
     readable by non-members):
     `GET /doctrine/versions?namespace=ns_doctrine&id=missing` →
     **exactly 200 with an empty array** (the query reaches the
     ordinary path; `DoctrineDocQuery` requires `id` — round 2 P2:
     without `&id=` the request is a 400 that never reaches
     authorization, and a bare not-403 assertion passes vacuously).
   - Control: the SAME request (with a written doc id if needed)
     against a plain `app(...)` (default configuration) → 403 (the
     doctrine authz gate on the default wall).
5. `configured_wall_keeps_doctrine_ingest_prohibition`
   - `app_with_walls` with doctrine = `ns_cfg_doctrine`; a
     doctrine:write token (no admin):
     `POST /doctrine?namespace=ns_cfg_doctrine` with a valid
     `DoctrineRequest` body → **403** — the explicit configured-wall
     ingest hits the doctrine prohibition (round 2 P2: the memory
     route never consults it).
   - Distinguisher: the same token POSTing `/doctrine` with
     `?namespace=` a non-private, non-configured org wall it holds
     membership in → succeeds (ingests as ordinary content) —
     proving the 403 is the doctrine prohibition, not a generic
     rejection.
6. `rollback_targets_configured_wall`
   - `app_with_walls` with doctrine = `ns_cfg_doctrine`; admin token;
     seed two revisions of a doctrine body via POST `/doctrine`
     (configured default), then unqualified `POST /doctrine/rollback`
     (no `?namespace=`) targeting that body — the rollback lands on
     the CONFIGURED wall (verify the archived revision and active
     body both live there; the old `ns_doctrine` wall stays empty).
