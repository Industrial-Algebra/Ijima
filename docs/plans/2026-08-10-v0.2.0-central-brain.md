# Ijima v0.2.0 — Central Brain (deployment release)

Date: 2026-08-10
Status: Proposed (scope agreed: thin clients now, satellite v0.3)
Depends on: PR #63 (GrantToken) merged

## Goal

Make Ijima production-ready for a full internal deployment on
**laniakea** (Ryzen 7 NAS, 64GB RAM, 1TB NVMe, 20TB ZFS pool, tailnet):
the central memory brain for Industrial Algebra, Kellas Cat Games,
Shiroyama Electric Music Company, and personal projects/writings, with
feeds from Minoru (mining) and Quantizon (experimental DLMs).

**Toplogy decision (2026-08-10):** all workstations — including Kaiizen —
run as **thin clients** (pi's `IJIMA_URL` points at laniakea; one
`IJIMA_TOKEN` grant each). Satellite instances with checkpoint sync are
**v0.3** (design seed in WS6).

## Gap analysis (what 0.1.0 lacks for this)

1. No deploy kit (systemd, config file, runbook, backups, TLS-on-tailnet).
2. `GrantToken` has **no expiry/revocation** — stateless signatures valid
   forever. Unacceptable on a long-lived multi-principal host.
3. Migration is single-source, dumps into one commons namespace, no
   cross-source dedup, no origin/provenance tagging, no trust defaulting.
4. Shared namespaces have **no membership** — any authenticated principal
   reaches any shared namespace via `resolve_ns`.
5. No batch ingest for machine feeds; mining trigger is per-session only.

## Workstreams

Sequencing: WS0 → WS1 → WS2 → WS3 → (WS4, WS5) → release. Each WS is
1–2 PRs. WS1 first: it makes laniakea testable early, so later workstreams
validate against the real host. WS6/WS7 are docs-only and may land after
the tag (see Release gate).

### WS0 — Proserpina agent upgrade (small, pre-release; Anima PULSE rec #3)

Flagged three consecutive pulses: the workspace pins `proserpina 0.3.0`
while `proserpina-agent 0.1.0` shipped Aug 10 **specifically to be
consumed by Ijima's LLM mining tier** — and the path is proven: the
Proserpina repo's own `agent/tests/ijima_surface.rs` compiles the exact
Ijima surface (`Agent, AgentId, Message, MessageKind, Persona,
ProserpinaError, HttpAgent/HttpConfig`) against the agent crate.

- [ ] Workspace `Cargo.toml`: `proserpina = "0.3.0"` →
      `proserpina-agent = "0.1.0"`.
- [ ] `ijima-miner/Cargo.toml` + `ijima-server/Cargo.toml`: dep + feature
      swaps (`dep:proserpina` → `dep:proserpina-agent`;
      `proserpina/backend-http` → `proserpina-agent/backend-http` in the
      `mining` feature).
- [ ] `ijima-miner/src/llm.rs`: `use proserpina::…` →
      `use proserpina_agent::…` (3 import sites; surface identical).
- [ ] Gates: `cargo test --all-features` (mining tier) + clippy.

### WS1 — Deployment kit (PR: `feature/deploy-kit`)

- [ ] `deploy/ijima.service` — systemd unit (hardened: `ProtectSystem`,
      `NoNewPrivileges`, `DynamicUser` or dedicated `ijima` user; data dir
      on NVMe, e.g. `/var/lib/ijima`).
- [ ] `deploy/ijima.toml.example` + **config-file support** in `serve`:
      TOML read from `$IJIMA_CONFIG`, `~/.ijima/ijima.toml`, or
      `/etc/ijima/ijima.toml` (env vars override; today is env-only).
      Keys: `host`, `port`, `data_dir`, `issuer_key`, `rate_base`,
      `rate_multiplier`, `embedding_model`.
- [ ] **Token revocation** (ADR at implementation): store-backed
      revocation set keyed by token-content hash; checked at
      `verify_bearer`; `ijima token revoke <bearer-or-hash>` (admin) +
      `ijima token revocations` (list). Expiry stays upstream — request
      GrantToken expiry in Schubert 0.5; revocation list covers the
      leaked-token kill-switch now.
- [ ] `docs/deploy/laniakea.md` — runbook: NVMe layout, ZFS snapshot
      schedule (`zfs-auto-snapshot` guidance), SurrealDB backup
      (`ijima export` as cold copy + surrealdb backup), tailscale TLS
      (`tailscale serve` in front, or MagicDNS cert + `tls` feature),
      embedding model cache location, upgrade procedure.
- [ ] `/status` extension: uptime, memory count, namespace count, last
      mining pass.
- [ ] **Dominic M4 enablement** (Anima PULSE 2026-08-17 rec #2): at
      deploy time, mint the dispatcher's service grant
      (`session:ingest` + `memory:read,write` + `knowledge:read,write`)
      and share the runbook — M4 (pi Dispatcher) becomes testable
      against live laniakea hardware instead of fixtures. Also retires
      the carried "async-agent validation under real pi sessions"
      open question once M4 runs.

### WS2 — Multi-source import (PR: `feature/import`)

Generalizes `migrate` → `ijima import`, targeting the **remote daemon**
(HTTP), since imports run from workstations against laniakea.

- [ ] `ijima import mempalace --db <path> --source <name> [--namespace ns]`
      — pi-mempalace and ZeroClaw SQLite sources (reuse row readers from
      `migration.rs`).
- [ ] **Provenance**: every imported memory tagged
      `origin = source-name`, harness `Pi`/`Other` (exists), authority
      per trust-tier defaulting: imported content lands as
      `MemorySource::AutoCapture` (existing conservative mapping) —
      promoted only via `trust:promote`.
- [ ] **Namespace routing**: default `ns_import_<source>` (one per
      workstation), not the global commons; `--namespace` overrides.
      Import into the caller's grant-checked namespace (memory:write).
- [ ] **Cross-source dedup**: content-hash (exists in store) + semantic
      check via the daemon's `POST /memories/check` before each store;
      import report `{added, deduped, skipped}` per source.
- [ ] Import ordering: run the 3 workstation imports sequentially;
      report shows per-source overlap (the same memory saved on multiple
      machines).

### WS7 — Block↔memory promotion boundary (design note; parallel, NOT a 0.2.0 gate)

Anima PULSE 2026-08-17 rec #6: Wallace 04 (block-structured sessions) and
Ijima's WS2 provenance model are converging on the same unanswered
question — **which of the Lonis §2.7 `Block` kinds (14) are
memory-promotable, and does promotion ride Ijima's existing trust tiers
(`AutoCapture` default + `trust:promote` to raise)?** Resolve it once, in
the doctrine, before two implementations disagree.

- [ ] Design note in neutral territory (`IA-documents/CONTRACTS/`,
      alongside `wallace-knopper-embedding.md`): per-block-kind
      promotability table; promotion path via the existing tier model;
      the miner's "no opaque strings" rule (§8.C) as the intake contract
      for block payloads.
- [ ] Inputs: Wallace doc 04, the Lonis `Block` contract (§2.7 /
      lonis-schema), Ijima `docs/adr/provenance-tier-model.md` + WS2
      import defaults.
- [ ] Feeds WS6 (satellite sync carries blocks as session turns) and the
      v0.3 federation design. Does not block the 0.2.0 tag.

### Release

**Gate (added per Anima PULSE 2026-08-17 bottleneck #3):** tag `v0.2.0`
once **WS0–WS3** are merged; WS4/WS5 ride along if ready (both small);
WS6/WS7 are docs-only and may land after the tag as fast-follows.
Rationale: published 0.1.0 on crates.io serves the deprecated
CapabilityToken auth model — develop's GrantToken verifier already
rejects 0.1.0 bearer blobs, so every day widens the gap between published
and real. Ship promptly; don't gold-plate.

- [ ] Version bump 0.2.0 (workspace crates), CHANGELOG
      (`[0.2.0] — Central Brain`), merge to develop, tag `v0.2.0`,
      publish.yml does the rest.
- [ ] Manual announcement blog post (per decision: announcements stay
      manual until the reusable workflow lands from another project).

## Risks / notes

- **GrantToken expiry is upstream** (Schubert): revocation list is the
  0.2.0 answer; expiry rides Schubert 0.5. Keep the revocation check
  cheap (in-memory hash set, hydrated from store at boot).
- **Import over HTTP** must respect rate limits — batch endpoint from
  WS4 may be reused; or the importer runs on laniakea itself
  (`ijima import` against localhost) with file transfer via scp/rsync.
  Plan for the latter as the default (simpler, no new surface).
- **Namespace membership** changes `resolve_ns` semantics — audit every
  route that resolves namespaces before merging WS3 (rooms, taxonomy,
  stats, palace graph all filter by project/topic, not ns — verify).
- ZFS: data dir on NVMe (fast), snapshots target the pool; SurrealDB
  compaction + snapshot interplay documented in the runbook.
